# 微信 4.1.13.61 偏移迁移手册

日期：2026-09-08 · 用时：约 3 小时（4.1.11.53 → 4.1.13.61）

## 成果

- `wechat_version/4_1_13_61_mac.json`：接收 + 文本发送全链路 17 个 hook 地址全部迁移并验证。
- `onebot/script.js`：Req2Buf 诊断 hook 改为可选（4.1.13 未定位，留空跳过，不影响发送）。
- 实测：attach 成功、接收 Hook 一次启用、文本工厂 13 地址全过、微信无崩溃。
- 未迁移（当前配置下不会被 attach）：req2bufEnter/Exit、blrX8（小程序发送链，EnableMiniProgramSend=false）、上传/下载簇（死代码，attach 函数无调用方）、realTextReq2Buf（诊断用）。

## 关键架构事实（避免下次重新踩坑）

1. **唯一的活脚本是 `onebot/script.js`**（Go text/template，JSON 整体注入）。`frida/` 目录下的脚本（含 receiver.js）全部是历史遗留死代码，其硬编码偏移无关紧要。
2. hook 启用开关：`EnableUnsafeSend`（文本发送 realText 链）、`EnableMiniProgramSend`（sendFunc/blrX8/req2buf）、`EnableMediaHooks`/`EnableMediaDownloadHooks`（媒体，且 attach 函数当前无人调用）。
3. 地址模板变量大多有 `{{if}}` 空值守卫；`req2bufEnterAddr` 等少数没有——**空值会导致 `baseAddr.add()` 语法错误使整个脚本失效**，未定位项必须保留旧值或改模板加守卫。
4. `setupRealTextSend` 的 `requiredAddresses` 空值即整体禁用文本发送（安全阀）。
5. 偏移=vmaddr（arm64 切片 `__TEXT` vmaddr=0），文件偏移 = fat_offset + 偏移。旧 arm64 切片在 fat 0xa344000，新在 0xaab0000。
6. ack 生命周期：`pendingBuf2RespTaskId` 由 buf2Resp（接收 hook）与超时清零，Req2Buf hook 仅诊断。

## 迁移方法论（按命中率排序）

1. **位级通配模式匹配**（capstone）：从旧函数头反汇编 ~28 条，屏蔽 ADRP/B/BL/CBZ 的立即数做唯一匹配。本轮命中 ~12 个（掩码精度关键：只屏蔽 imm12 位 21-10，保留 Rn/Rt；屏蔽寄存器会歧义爆炸）。
2. **簇内联合一致性**：同簇函数（realText 家族）候选间新间距 ≈ 旧间距（±0x600）联立求解。SendAsync→SubmitAsync 新旧间距完全一致（0x204）。
3. **函数体 DP 对齐**：对已确认的函数对（如 SendAsync 新旧地址）做 Needleman-Wunsch 掩码对齐（match+2/gap-1/miss-2），把旧 BL 调用点映射到新 BL 读出被调函数新地址（RequestCtor 就这么定的，随后并排反汇编复核）。
4. **调用方区域内部 BL 目标表**：列出已知家族区域（如新 0x21f3000-0x21f5000）内全部 BL 目标——proto 调用与 autoBufferWrite 调用相距 0x24 的模式直接暴露了新 Encoder 位置（0x21f41e4，注意新栈帧 #0x50 不同于克隆的 #0x40，按 prologue 形状搜索会漏）。
5. **dtor/ctor 呼叫关系**：PayloadDtor 由 ctor 在 +0xE4 调用（旧 +0xdc），且形状（stp x20,x19,[sp,#-0x20]!…adrp+add→str [x0]）逐指令一致 → 0x21f4308。
6. **失败的方法**：链式修复指针解码反查 vtable（格式假设不对）、__DATA QWORD 搜索、IDA 没用上（IDA Free 9.1 在机，未尝试 headless）。

## 陷阱记录

- `req2bufEnterAddr` 等 JSON 值指向**大函数中部**（std::map 红黑树循环），不是函数头——按函数头做模式匹配必然失败，且新版本寄存器分配会变（x24→其他）。
- 模板实例化：encoder 逻辑被克隆 16+ 份（字节级仅 BL 相对偏移不同），必须靠调用上下文区分。
- 编译器会重排/内联：新 Encoder 头部多了 helper 调用；旧"encoder 函数"的判定要靠内部 BL 序列而非 prologue。
- 监控 `tail -f` 一定要 `tail -n 0`，否则重放整个日志历史。

## MMStartTask 真实结构（62/63 实验的重大认知修正）

上游 weixin-macos 的"MMStartTask 416 字节模板"在 4.1.13 的完整图景（日志命名空间 **mars::mmext** = 微信官方扩展接口，方向没错）：

- **壳**（63=0x55d1734）：日志 + `ldr x20,[x0,#0x18]` 取 inner → `bl 0x5609d44`(62=0x5609b24) 真主体 → 返回 inner!=NULL
- **真主体**：`TaskWrapper(sp+0x38, task)`（构造函数 0x59fce0c 经 x1 隐式收 task）→ 提交 `inner->0x68` 队列（0x59afacc）。**同步段不解引用 task 字段**——序列化在队列消费线程异步发生
- **notifyack 正道样板**（62=0x55d2724）：`0x55d237c(manager,字符串)` 初始化任务 + `0x55d4230` 填充 + `0x55d3dac(task+0x70, 回调, 0x86eb528, ...)` 注册回调 → MMStartTask。**任务由调用方构造，不是 MMStartTask 内部**
- 实测结论链：61 硬编码模板 → 崩 0x0/悬垂；reportkv 一次性任务模板 → 崩 0x4001...（外部对象已释放）；newsync 0x1A0 模板 → 崩 0x200（缺字段/长度不足）；**newsync 0x300 模板 → 提交成功不崩**（但注入点不在消费路径，消息未达）
- **注入点 0x2ea7xxx 序列化器与 MMStartTask 队列消费无关**（挂载后累计 0 命中，带计数器实锤）——它是别的 CGI 路径的编码器。发送注入需要逆向队列消费者，或改走 notifyack 三件套原生构造
- **【22:12 决定性突破】write 函数注入法打通管道**：挂 autoBufferWrite 本体（63=0x4308c58，全任务序列化必经），克隆任务 MMStartTask 提交后 1.5s 窗口期内 write 首次调用即本任务序列化——**直接换写 x1(data)/x2(len) 为我们的 protobuf**。实测连续命中（112/174 字节两次换写，微信稳定不崩）。任务提交→序列化→网络发送管道全通。剩余：①4.1.13 文本线格式适配（BuildTextMsgProto 仍为 4.1.6 shape，服务器可能拒收）②ACK 识别恢复（realText 链禁用中，API 报 timeout 为误报，实际已发出）
- **script.js 语法校验法**（Go test 因 frida-core-devkit 缺失不可用）：python 渲染模板（{{.x}}→"0x1000"，{{if}}A{{else}}B{{end}}→B 跨行非贪婪迭代）→ `node --check /tmp/script_rendered.js`。编辑 script.js 后必做——FATAL "Script(line N): SyntaxError" 会导致整个会话零挂载

- swap hook（序列化器**函数头** 0x2ea7c00）在 62 导致微信 4 秒退出——已永久摘除；注入点（函数**内部** call site 0x2ea7d9c）挂载安全。

- **脏 detach 症状链定论**：活微信上 stop onebot（接收 hook 在热路径常触发）→ 卸载必超时 → 下个会话 attach 成功但装备挂死。唯一恢复 = 完整净循环。绝不在活微信上反复 stop/start 重试。

- **克隆模板只能用 newsync 任务**：x1 模板里的外部指针（指向任务消息对象等）在一次性任务（reportkv/pushlog 等）完成后被释放，克隆体带着悬垂指针调 MMStartTask → access violation 0x4001...（实测）。newsync 是 longlink 同步循环任务，微信持续重发、对象长期存活，克隆安全。采样器应过滤 `cgi 包含 /newsync` 并持续刷新模板保持新鲜。
- **X0 捕获要放在 sendFunc 入口 hook**：sendFunc+0x10 的独立 hook 在部分会话永不触发（入口 hook 的重定位块交互问题，机理未完全定论），实测入口 hook 每次任务必触发，X0 刷新合并进 setupRealX1Capture 一劳永逸。
- **自动登录（62 实测）**：强杀重开后登录窗口按钮名为「进入微信」（AX 匹配"录"会失败），位置约屏幕 50% 宽、54.5% 高；点击前必须 `tell application "WeChat" to activate`（否则点击被前台应用吃掉）。登录成功的判据是网络任务起流（x1 样本出现），不是窗口名（登录窗口也叫"微信"）。

### 新增通用方法论（本轮验证有效）

1. **家族 BL 调用点普查**（本轮最强新工具）：对候选地址统计全二进制 BL 被调次数——真函数有大量调用（数百），旧地址在新版中**零残留调用**即证已漂移。再加成对惯用法检查（data/length 100% 配对）可定案。
2. **区域均匀平移假设**：先确认 1-2 个锚点的 shift，同区域其余地址按同 shift 推定，再用局部特征（BL 目标、帧偏移、vtable 形状）逐一验证。本轮 0x42e4xxx~0x4308xxx 整区 +0x578 一次通过。
3. **死孪生陷阱**：位级匹配可能命中指令孪生（死代码）——11 的 buf2Resp 函数头匹配到 62 的 0x430761c（恰=61 死孪生 0x43070a4+0x578），但活接收点在 0x42e4e18。区分：活点附近有对**活** write 函数的 BL；死孪生区无真实流量命中。
4. **sendFunc 不可区域平移**：跨版本漂移量大且无规律（11→61 +0x3b0fdc，61→62 +0x560），必须位级匹配。
5. **升版自检清单（启动后 10 秒内判生死）**：① recv-sample 出现=接收点+data/length 全对 ② real-x1 采样出现=sendFunc 对 ③ 两者全无=地址有错，别等。
